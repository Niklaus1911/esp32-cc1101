Fewer phantom receptions from noisy receivers, and diagnostics that show whether a receiver's signal is reaching the board at all.

## What changed

- **Receiver noise no longer fills the history.** Superheterodyne modules without squelch (RX470C, RXB6 and similar) output constant random noise. Now and then a burst of it was accepted as a short 4–6-bit code (for example `0x0`, 4 bits) and added to **Recent**. A code seen only once in a capture must now carry at least 8 bits. Short codes that repeat within a capture are still accepted, and normal 12–32-bit remotes are unaffected. In host tests on 500,000 random noise captures, false receptions dropped from 23 to 0, while simulated presses of real 24-bit remotes decode exactly as before.
- **RX line diagnostics.** `/api/live` adds these fields under `radio`:
  - `captures`: completed RMT captures, counted before decoding.
  - `capture_open_ms`: how long the current receive has been waiting.
  - `line_samples`, `line_high`, `line_edges`: samples of the RX DATA pin taken while idle.

  A capture starts on an edge and ends only after 30 ms of silence, so a pin stuck at one level used to leave every counter at zero, which looked like a dead receiver. Now the cause is visible:
  - always high with no edges: the receiver output is held high, for example a module with VCC connected but no GND;
  - always low with no edges: no receiver output reaches the pin;
  - a healthy receiver shows a mix of levels with steady edges.
- **Decoder tests on the PC.** The capture decoder moved into its own file with no ESP-IDF dependencies, and its Unity tests now also run as host tests (`rf_ook_host_tests`). This includes a noise test that fails on the old decoder.

v1.3.0 installs over v1.0.x, v1.1.x and v1.2.x by OTA, and existing signals, rules, history and settings are kept.

**Full changelog:** https://github.com/Niklaus1911/esp32-cc1101/compare/v1.2.0...v1.3.0

Each zip contains the application image, bootloader, partition table, initial OTA data, a `flash_args` file with offsets, checksums and license notices. The standalone `rfbridge-v1.3.0-<profile>.bin` assets are the same application images, provided for OTA. `SHA256SUMS` covers every asset.

### Update from an earlier release (OTA)

Use **Web UI > System > Firmware update** with `rfbridge-v1.3.0-<profile>.bin`, or from a source checkout:

```bash
tools/push-ota.sh <hostname>.local rfbridge-v1.3.0-<profile>.bin
```

The device must be on Wi-Fi in service mode `web` or `both`, and the image's profile must match the running board. OTA writes the image to flash as it arrives, so a weak Wi-Fi link can drop the upload. If that happens, the device keeps running its current firmware and you can retry from a better position.

### First install, or a board running other firmware (wired)

Extract the zip for your board, then from inside that folder:

```bash
# Optional but recommended if the board already holds learned signals or network settings:
esptool --chip <esp32|esp32s3> --port <serial-port> read-flash 0x9000 0x6000 nvs-backup.bin

esptool --chip <esp32|esp32s3> --port <serial-port> write-flash @flash_args
```

`flash_args` preserves NVS at `0x9000` (size `0x6000`). **Do not run `erase-flash`**, and do not merge these files into one image: padding the gap between the partition table and OTA data would wipe NVS.

## Safety

The Web UI, OTA endpoint and Wi-Fi setup are intentionally unauthenticated. Anyone on the LAN can control the radio, install firmware or move the device to another network. Only run it on a trusted network and never expose port 80 to the Internet. Use the CC1101 at 3.3 V only, always with an antenna, and follow your local RF regulations. Power generic receiver modules at 3.3 V and always connect their GND.
